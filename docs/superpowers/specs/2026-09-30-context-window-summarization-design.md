# Context Window & Summarization — Design Spec

Date: 2026-09-30
Scope: `apps/api` (Prisma schema, migration, chats, ollama, config), `packages/contracts`, `packages/api-client`, `apps/web` (chat feature).

## 1. Background

The LLM is stateless: every request resends conversation history. Today
`ChatStreamService.limitHistory` sends the newest completed turns up to
`CHAT_MAX_HISTORY_MESSAGES` (100) and `CHAT_MAX_HISTORY_CHARS` (100 000) and
silently drops anything older. Two problems:

- The limit is in characters, but the model limit is in tokens. 100k chars of
  history plus a 12k-char message can exceed the model context, and Ollama then
  silently truncates the start of the prompt.
- `num_ctx` is never sent, so the effective context size depends on each
  machine's Ollama default (32 768 on the dev machine, can be much lower).

## 2. Goals

1. Per-model configuration stored in the database (`name`, `max_context`), used
   as the single model allowlist.
2. A token-budgeted sliding window that folds old turns into a running summary
   instead of dropping them.
3. The UI shows current context / max context and where the summary begins.

### Success criteria

- Every Ollama call sends `options.num_ctx = model.max_context`.
- A prompt never exceeds `max_context`; when history grows past the trigger,
  older turns are summarized and the summary is sent as a system message.
- The meter by the composer shows `used / max` tokens and updates live after
  each turn; switching model updates the max immediately.
- A divider in the message list marks where the model's exact memory begins,
  expandable to show the summary.
- A failed summarization never fails the user's message.
- `pnpm lint && pnpm typecheck && pnpm test && pnpm build && pnpm openapi:check` pass.

### Non-goals

- No admin UI or API for editing models (rows managed by migration / SQL).
- No tokenizer on the Node side; token counts are estimated, then corrected by
  Ollama-reported counts.
- No background/asynchronous summarization.
- No per-model settings beyond `name` and `max_context`.
- `Message.model` is not converted to a foreign key.

## 3. Decisions (user-approved)

| Topic                  | Decision                                                                                     |
| ---------------------- | -------------------------------------------------------------------------------------------- |
| Max context source     | `max_context` column on a new `Model` table, sent as `num_ctx`                               |
| Model allowlist        | `Model` table is the only source of truth; `OLLAMA_ALLOWED_MODELS` removed                   |
| Default model          | Stays in `OLLAMA_DEFAULT_MODEL`; must match a `model` row (checked at startup)               |
| `Chat.selected_model`  | Replaced by `selected_model_id` FK to `model`                                                |
| `Message.model`        | Stays a plain string (historical record)                                                     |
| Public API model field | Stays `selectedModel: string` (the model name); repository resolves name ↔ id                |
| Summarization timing   | Inline, before generation, inside the chat generation lock, after `stream.started`           |
| Summarizer model       | The chat's selected model                                                                    |
| Thresholds             | Trigger at 75% of `max_context`, fold down to ~40%, always keep the last 4 messages verbatim |
| Token estimate         | `ceil(chars / 3)`, self-corrected by the last reported `promptTokens + completionTokens`     |
| UI                     | Meter by the composer + "Earlier messages summarized" divider with expandable summary        |

## 4. Data model

Conventions follow `schema.prisma`: PascalCase model names mapped with
`@@map` to singular snake_case tables, snake_case fields with no field-level
`@map`, UUIDv7 ids generated by PostgreSQL.

```prisma
model Model {
  id          String   @id @default(dbgenerated("uuidv7()")) @db.Uuid
  name        String   @unique @db.VarChar(200)
  max_context Int
  created_at  DateTime @default(now()) @db.Timestamptz(3)
  updated_at  DateTime @updatedAt @db.Timestamptz(3)
  chats       Chat[]   @relation("model_chats")

  @@map("model")
}

model Chat {
  // ...existing fields, minus selected_model
  selected_model_id String       @db.Uuid
  selected_model    Model        @relation("model_chats", fields: [selected_model_id], references: [id], onDelete: Restrict)
  summary           ChatSummary? @relation("chat_summary")

  @@index([selected_model_id])
}

model ChatSummary {
  id                            String   @id @default(dbgenerated("uuidv7()")) @db.Uuid
  chat_id                       String   @unique @db.Uuid
  content                       String   @db.Text
  summarized_through_message_id String   @db.Uuid
  token_count                   Int
  created_at                    DateTime @default(now()) @db.Timestamptz(3)
  updated_at                    DateTime @updatedAt @db.Timestamptz(3)
  chat                          Chat     @relation("chat_summary", fields: [chat_id], references: [id], onDelete: Cascade)
  summarized_through_message    Message  @relation("summary_through_message", fields: [summarized_through_message_id], references: [id], onDelete: Cascade)

  @@map("chat_summary")
}
```

`Message` gains the back-relation field for `summary_through_message`.

`Model` may collide with Prisma-generated names. Verify on the first
`prisma generate`; if it does, rename the Prisma model to `LlmModel` and keep
`@@map("model")`.

### Migration (single, hand-reviewed)

1. Create `model`; insert `('qwen2.5:1.5b', 8192)`.
2. Insert a `model` row (`max_context = 8192`) for every distinct
   `chat.selected_model` not already present, so the backfill cannot fail.
3. Add `chat.selected_model_id` nullable, backfill by joining on name, set
   `NOT NULL`, add FK (`ON DELETE RESTRICT`) and index, drop `selected_model`.
4. Create `chat_summary` with its unique index and FKs.

## 5. Model registry (`apps/api/src/ollama`)

- New `models.repository.ts`: `findAll()`, `findByName(name)`.
- `OllamaService`:
  - `listModels()` returns `model` rows that are also installed in Ollama, as
    `{ name, default, maxContext }`.
  - `assertAllowed(name)` becomes async and returns the `Model` row (throws
    `MODEL_NOT_ALLOWED` if no row).
  - `onModuleInit` checks that `OLLAMA_DEFAULT_MODEL` has a row; throws
    otherwise so the API fails fast.
- `environment.schema.ts`: remove `OLLAMA_ALLOWED_MODELS` and its refinement;
  remove `CHAT_MAX_HISTORY_MESSAGES` and `CHAT_MAX_HISTORY_CHARS`; add:
  - `CHAT_CONTEXT_SUMMARIZE_AT_RATIO` (default `0.75`)
  - `CHAT_CONTEXT_TARGET_RATIO` (default `0.4`)
  - `CHAT_CONTEXT_KEEP_RECENT_MESSAGES` (default `4`)
  - `CHAT_CONTEXT_CHARS_PER_TOKEN` (default `3`)
  - `CHAT_CONTEXT_SUMMARY_MAX_RATIO` (default `0.1`)
  - refinement: `TARGET_RATIO < SUMMARIZE_AT_RATIO`.
- `.env.example` updated to match.
- `ChatsRepository` resolves `selectedModel` names to `selected_model_id` on
  create/update and includes `selected_model.name` when reading chats.

## 6. Ollama client

- `OllamaHistoryMessage.role` gains `'system'`.
- `StreamOllamaChatParams` gains `contextTokens: number` → sent as
  `options.num_ctx`.
- New non-streaming `complete({ model, messages, contextTokens, maxTokens, signal })`
  returning `{ content, promptTokens, completionTokens }`, sending
  `stream: false` and `options.num_predict = maxTokens`. Same timeout and error
  mapping as `streamChat`.

## 7. Context engine (`apps/api/src/chats`)

### Units

- `context-window.helpers.ts` — pure functions:
  - `estimateTokens(text, charsPerToken)`
  - `estimatePromptTokens({ summary, turns, content })` (adds a small
    per-message overhead)
  - `needsSummarization({ estimate, lastReported, newContentEstimate, trigger })`
    — true when `max(estimate, lastReported + newContentEstimate) > trigger`
  - `selectTurnsToFold({ turns, keepRecent, target })` — oldest completed turns
    to fold so the remaining prompt is ≤ target, never folding the last
    `keepRecent` messages and never splitting a user/assistant pair.
  - `chunkForSummarization({ previousSummary, turns, budget })`
- `chat-summary.repository.ts` — `findByChatId`, `upsert`.
- `context-window.service.ts` — `buildPrompt({ chat, model, content, signal, onSummarizing })`
  returns `{ messages, summary }`.

### History cache

`ChatHistoryEntry` gains `id` (message id) so turns after
`summarized_through_message_id` can be selected from cache. The zod schema in
`ChatHistoryService` is updated; old cache entries without `id` fail parsing
and are reloaded from the database (existing invalidate path).

### Algorithm (per message)

Let `max = model.max_context`, `trigger = max × SUMMARIZE_AT_RATIO`,
`target = max × TARGET_RATIO`.

1. Load the summary (if any) and completed turns after
   `summarized_through_message_id`.
2. If the new message alone estimates above `trigger` → `413 Payload Too Large`
   ("The message is too long for this model's context.").
3. Estimate the prompt `[system: summary] + turns + new message`. If
   `needsSummarization` is false → return it.
4. Otherwise call `onSummarizing()` (emits `context.summarizing`), select turns
   to fold, and summarize `previous summary + folded turns` with the chat's
   model via `complete()`, `num_predict = max × SUMMARY_MAX_RATIO`. If the fold
   input exceeds the budget, summarize it in sequential chunks, each step
   feeding the previous result forward.
5. Upsert `chat_summary` (`content`, `summarized_through_message_id` = last
   folded message, `token_count` = reported completion tokens).
6. Return `[system: "Summary of the earlier conversation: …"] + remaining turns + new message`.

The summarization prompt instructs the model to preserve facts, decisions,
names, numbers, user preferences, and open questions, written in the
conversation's language, as concise prose.

### Integration into `ChatStreamService.stream`

- Model resolved via `ollama.assertAllowed(name)` → `Model` row.
- `buildPrompt` runs after `stream.started` (message rows exist, so cancel and
  error use the existing `endGeneration` paths) and before `streamChat`.
- `streamChat` receives `contextTokens: model.max_context`.
- After `message.completed`, emit `context.updated`.
- `limitHistory` and the history-char/message config are removed.

### Failure handling

| Case                                   | Behaviour                                                                                 |
| -------------------------------------- | ----------------------------------------------------------------------------------------- |
| Summarization errors / times out       | Log warning; fall back to dropping oldest turns until prompt ≤ trigger; reply continues   |
| User cancels during summarization      | Summary not saved; existing cancellation path (`stream.cancelled`)                        |
| New message alone exceeds trigger      | 413 before generation                                                                     |
| Estimate was too low last turn         | Self-correction via reported tokens forces summarization on the next turn                 |
| Switch to a model with smaller context | Next turn re-evaluates against the new `max_context`; chunked fold handles large backlogs |
| Existing long chats (no summary yet)   | First over-budget turn folds the backlog in chunks                                        |

## 8. Contracts & API

`packages/contracts`:

```ts
interface ModelInfo { name: string; default: boolean; maxContext: number }

interface ChatContext {
  usedTokens: number | null;       // last completed turn: promptTokens + completionTokens
  maxTokens: number;               // selected model's max_context
  summary: string | null;
  summarizedThroughMessageId: string | null;
}
// Chat response gains: context: ChatContext

type ChatStreamEventName = ... | 'context.summarizing' | 'context.updated';
// { event: 'context.summarizing'; data: Record<string, never> }
// { event: 'context.updated'; data: ChatContext }
```

`context.updated` is emitted after a summary is saved and after
`message.completed`. DTOs (`chat-response.dto.ts`, `models-response.dto.ts`)
updated; OpenAPI and `api-client` regenerated.

## 9. Web (`apps/web/src/features/chat`)

- `context-meter.tsx` (new), rendered by the composer:
  - text `6.1k / 8.2k tokens`, thin progress bar, amber at ≥ 75%
  - tooltip / `title` with exact numbers; accessible label
  - `— / 8.2k` when `usedTokens` is null
  - max comes from the selected model's `maxContext`, so it updates on model switch
- `message-list.tsx`: "Earlier messages summarized" divider after
  `summarizedThroughMessageId` (if that message is loaded), collapsed by default,
  expands to show the summary text.
- `use-chat-stream.ts` / `chat.helpers.ts`:
  - `PendingStream.status` gains `'summarizing'`; shows "Summarizing earlier
    messages…" in place of the thinking indicator
  - `context.updated` writes `context` into the cached chat query data
- Follows existing styling (Tailwind only, light/dark tokens, reduced motion).

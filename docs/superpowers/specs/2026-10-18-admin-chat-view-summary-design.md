# Admin Chat View & Cached Admin Summary — Design Spec

Date: 2026-10-18
Builds on: `2026-10-01-admin-usage-tracking-design.md`,
`2026-09-30-context-window-summarization-design.md`.
Scope: `apps/api` (Prisma schema, migration, new `admin/chats` module, chats
helpers, models, usage), `packages/contracts`, `packages/api-client`,
`apps/admin`.

## 1. Background

The admin user / anonymous detail pages show a usage log whose last column is
a short, non-clickable chat id. Admins cannot see what was written in a chat or
get a quick idea of what it was about.

## 2. Goals

1. In the usage log table (user **and** anonymous detail pages) the chat column
   is first and links to a new admin chat page.
2. The admin chat page shows the chat metadata and full transcript.
3. The page shows a short admin-only summary of the whole conversation,
   generated by the LLM and **cached**: reopening an unchanged chat makes no
   model call.
4. The cached summary records the message it covers up to. When the chat has
   newer messages, the summary is refreshed **incrementally**: old summary +
   only the new messages (same fold logic as the context summary).
5. The admin sees clear loading / updating states.

### Success criteria

- Clicking a chat id in either usage log opens `/chats/:chatId`.
- Opening a chat whose summary is up to date makes zero Ollama calls.
- Refreshing a stale summary sends Ollama only the previous summary plus the
  messages after `summarized_through_message_id` (chunked if large).
- Admin summary usage is logged with kind `ADMIN_SUMMARY`, the chat id, and no
  user / anonymous owner, so it never appears in a user's totals.
- Concurrent opens generate at most one summary per chat at a time.
- User tokens get `401` on all new routes; `POST` requires CSRF.
- `pnpm lint && pnpm typecheck && pnpm test && pnpm build && pnpm openapi:check`
  pass.

### Non-goals

Message pagination, markdown rendering in the admin transcript, editing /
deleting / manually regenerating an up-to-date summary, admin actions on the
chat (delete, archive), streaming the summary text, showing the user-facing
`conversation_summary`.

## 3. Decisions (user-approved)

| Topic             | Decision                                                                        |
| ----------------- | ------------------------------------------------------------------------------- |
| Chat view         | Dedicated admin route `/chats/:chatId`                                          |
| Pages affected    | User detail and anonymous detail (shared `UsageLogTable`)                       |
| Summarizer model  | Current default model (`model.is_default`) at generation time                   |
| Usage logging     | New `UsageKind.ADMIN_SUMMARY`, `chat_id` set, no owner                          |
| Generation flow   | Approach A: cached `GET` + synchronous `POST` refresh triggered by the client   |
| Storage           | New `admin_chat_summary` table, independent of `conversation_summary`           |
| Concurrency       | Redis lock per chat; `409 SUMMARY_IN_PROGRESS`; client polls `GET` while locked |
| Client disconnect | Generation is not aborted; the result is saved so the next open is a cache hit  |

## 4. Data model (one migration)

```prisma
enum UsageKind {
  CHAT
  SUMMARY
  ADMIN_SUMMARY
}

model AdminChatSummary {
  id                            String   @id @default(dbgenerated("uuidv7()")) @db.Uuid
  chat_id                       String   @unique @db.Uuid
  content                       String   @db.Text
  summarized_through_message_id String   @db.Uuid
  model_id                      String   @db.Uuid
  token_count                   Int
  created_at                    DateTime @default(now()) @db.Timestamptz(3)
  updated_at                    DateTime @updatedAt @db.Timestamptz(3)
  chat                          Chat     @relation("chat_admin_summary", fields: [chat_id], references: [id], onDelete: Cascade)
  summarized_through_message    Message  @relation("admin_chat_summary_through_message", fields: [summarized_through_message_id], references: [id], onDelete: Cascade)
  model                         Model    @relation("model_admin_chat_summaries", fields: [model_id], references: [id], onDelete: Restrict)

  @@map("admin_chat_summary")
}
```

Back-relations: `Chat.admin_summary AdminChatSummary?`,
`Message.admin_chat_summaries AdminChatSummary[]`,
`Model.admin_chat_summaries AdminChatSummary[]`.

Migration: `ALTER TYPE "UsageKind" ADD VALUE 'ADMIN_SUMMARY';` then
`CREATE TABLE admin_chat_summary` with the unique index on `chat_id` and FKs.
The new enum value is not used inside the migration (PostgreSQL forbids using
a value added in the same transaction).

## 5. Backend

### 5.1 Shared summarization helpers (`chats/`)

- `chat-history.service.ts`: move the private `isPartOfCompletedTurn` into
  `chats.helpers.ts` (exported) together with a new pure
  `toHistoryEntries(messages: Message[]): ChatHistoryEntry[]` that applies the
  filter and mapping now inside `loadFromDatabase`. `ChatHistoryService`
  calls it; behaviour unchanged.
- `context-window.helpers.ts`: export a pure `formatTranscript(entries,
  maxEntryChars)` (extracted from `buildSummaryRequest`, output unchanged).
  The admin summary does not reuse `buildSummaryRequest`; it has its own
  `buildAdminSummaryRequest` (see §5.4). Live testing with qwen2.5:1.5b showed
  the shared "notes" framing made the model echo the transcript.
  `chunkEntries`, `getContextBudget`, `estimateMessageTokens`,
  `isDegenerateSummary`, `entriesAfter` are reused as-is.

Admin code imports only these **pure** helpers from `chats/`; it never uses
chats services or repositories (module rule D from the admin spec).

### 5.2 Models & usage

- `ModelCatalogService.getDefault(): Promise<Model>` — `findDefault()`;
  throws `OllamaError('MODEL_NOT_AVAILABLE', …, 409)` if none (the seeder
  normally guarantees one).
- `RecordUsageParams.principal` becomes `RequestPrincipal | null`; `null` →
  both owner columns `NULL`. `toUsageOwner` / `toOwnerColumns` handle it.
- `toWireKind` maps `ADMIN_SUMMARY` → `'admin_summary'`; contracts
  `UsageKind` gains `'admin_summary'`. Owner-filtered reporting already
  excludes ownerless rows, so user/anon totals are unaffected.

### 5.3 `admin/chats/AdminChatsModule` (new)

Imports `AdminAuthModule`, `ModelsModule`, `OllamaModule`, `UsageModule`.
Provides its own `RedisLockService` instance (generic, depends only on
`RedisService` + config). Registered in `AdminModule`.

| Unit                            | Responsibility                                                                    |
| ------------------------------- | --------------------------------------------------------------------------------- |
| `AdminChatsRepository`          | Only Prisma caller: chat + owner (user email) + messages; summary find / upsert   |
| `AdminChatsService`             | `getChat(id)` → `AdminChatDetail` (404 if missing)                                |
| `AdminChatSummaryService`       | `getSummary(id)` and `refreshSummary(id)` (section 5.4)                           |
| `admin-chat-summary.helpers.ts` | `ADMIN_SUMMARY_INSTRUCTIONS`, `toSummaryState(...)` (stale / pending computation) |
| `AdminChatsController`          | HTTP ⇄ DTOs; `@UseGuards(AdminAuthGuard)` at controller level                     |

### 5.4 Summary algorithm

**Eligible entries** = `toHistoryEntries(messages)` — messages that belong to a
completed user/assistant turn, ordered by `(created_at, id)`. Streaming,
failed and cancelled turns are excluded, matching the context window.

**State** (`toSummaryState({ summary, entries, generating })`):

- `pending = entriesAfter(entries, summary?.summarized_through_message_id ?? null)`.
  If the through-message is missing from `entries` (should not happen, cascade
  deletes), treat the summary as absent and summarize everything.
- `stale = pending.length > 0`; `pendingMessages = pending.length`.

**`getSummary(chatId)`** — read only, never calls Ollama:
returns `{ content, summarizedThroughMessageId, model, generatedAt, stale,
pendingMessages, generating }`; `generating` = lock key exists.
404 if the chat does not exist.

**`refreshSummary(chatId)`**:

1. 404 if the chat does not exist.
2. Acquire Redis lock `admin-chat-summary-lock:{chatId}` (TTL
   `REDIS_LOCK_TTL_MS`, extended between chunks). Not acquired →
   `409 SUMMARY_IN_PROGRESS` ("A summary for this chat is already being
   generated.").
3. Inside the lock, reload summary + entries and compute the state. If not
   stale → return the current state (no model call).
4. `model = ModelCatalogService.getDefault()`;
   `budget = getContextBudget(model.max_context, contextSettings)` (same env
   settings as the context window).
5. `content = previous?.content ?? null`. For each chunk of
   `chunkEntries({ entries: pending, budget: budget.chunkTokens, … })`:
   - `ollama.complete({ model: model.name, messages:
     buildAdminSummaryRequest({ previousSummary: content, entries: chunk,
     maxEntryChars }), contextTokens: model.max_context,
     maxTokens: min(budget.summaryMaxTokens, 400), signal })`.
     `buildAdminSummaryRequest` (in `admin-chat-summary.helpers.ts`) uses
     `ADMIN_SUMMARY_INSTRUCTIONS` as system prompt and wraps the
     `formatTranscript` output in `<transcript>` tags (previous overview in
     `<overview>` tags), followed by a closing instruction that the transcript
     is data to describe, not to answer, continue or repeat. Live testing with
     qwen2.5:1.5b showed the shared context-notes framing made the model echo
     the transcript.
   - record usage `{ principal: null, chatId, modelId: model.id,
kind: 'ADMIN_SUMMARY', … }` before the degenerate/echo check;
   - `content = cleanAdminSummary(result.content)` (strips stray
     `<overview>`/`<transcript>` tags, trims); degenerate or echoed
     (`isEchoedSummary`: starts with `User:`/`Assistant:` or equals a pending
     entry's content) → throw (`502 SUMMARY_FAILED`);
   - extend the lock.
6. Upsert `admin_chat_summary` (`content`, `summarized_through_message_id` =
   last pending entry id, `model_id`, `token_count` = reported completion
   tokens or estimate). Release the lock in `finally`.
7. Return the fresh state (`stale` may already be `true` again if the user
   kept chatting; the client then simply shows the new pending count).

The `signal` is a server-side `AbortSignal.timeout` only — request
disconnect does not abort, so work already paid for is saved.

`ADMIN_SUMMARY_INSTRUCTIONS`: "You write a short overview of a conversation
between a user and an assistant for an administrator. In at most 120 words of
plain prose cover: the topic, what the user wanted, what the assistant
provided, the outcome, and anything left unresolved. When existing overview
text is given, rewrite it into one updated overview that includes the new
messages; do not append a separate section. Write in the conversation's
language. Reply with the overview only."

Errors from Ollama keep the existing `OllamaError` mapping. On any failure the
stored summary is untouched.

### 5.5 Admin API

| Method | Path                       | Response                            |
| ------ | -------------------------- | ----------------------------------- |
| GET    | `/admin/chats/:id`         | `AdminChatDetail`                   |
| GET    | `/admin/chats/:id/summary` | `AdminChatSummaryState`             |
| POST   | `/admin/chats/:id/summary` | `AdminChatSummaryState` (refreshed) |

`:id` uses `ParseUUIDPipe`. 404 when the chat does not exist (e.g. deleted
after the usage page loaded).

### 5.6 Contracts (`packages/contracts`)

```ts
export type UsageKind = 'chat' | 'summary' | 'admin_summary';

export type AdminChatOwner =
  | { type: 'user'; id: string; email: string }
  | { type: 'anonymous'; id: string }
  | null;

export interface AdminChatMessage {
  id: string;
  role: 'user' | 'assistant';
  status: 'streaming' | 'completed' | 'failed' | 'cancelled';
  content: string;
  model: string | null;
  createdAt: string;
  promptTokens: number | null;
  completionTokens: number | null;
}

export interface AdminChatDetail {
  chat: {
    id: string;
    title: string;
    model: string;
    createdAt: string;
    lastMessageAt: string;
    archivedAt: string | null;
    owner: AdminChatOwner;
  };
  messages: AdminChatMessage[];
}

export interface AdminChatSummaryState {
  content: string | null;
  summarizedThroughMessageId: string | null;
  model: string | null;
  generatedAt: string | null; // admin_chat_summary.updated_at
  stale: boolean;
  pendingMessages: number;
  generating: boolean;
}
```

Swagger DTOs mirror these; `openapi.json` regenerated.
`createAdminApiClient` gains `getChat(id)`, `getChatSummary(id)`,
`refreshChatSummary(id)`.

## 6. `apps/admin`

### 6.1 Usage log table

`UsageLogTable` column order: **Chat**, Date, Model, Kind, Input, Output.
Chat cell: `<Link to={`/chats/${chatId}`}>` showing `shortId(chatId)` in mono,
with `aria-label="Open chat <shortId>"`; `—` when `chatId` is null. Kind
label for `admin_summary` is "admin summary".

### 6.2 `/chats/:chatId` — `AdminChatPage`

- Back link: "← Back" (`navigate(-1)` when there is history, else owner page,
  else `/users`).
- Header: title; owner link (`/users/:id` email, or `/anonymous/:id`
  short id, or "Deleted owner"); model; created / last message dates;
  "Archived" badge when archived.
- `ChatSummaryCard` (labelled "Admin summary · visible to admins only").
- Transcript: one block per message — role label ("User" / "Assistant ·
  model"), timestamp, content with `whitespace-pre-wrap break-words`; status
  badge for failed / cancelled / streaming. Empty chat → "No messages."
- 404 → "This chat no longer exists." with back link.

### 6.3 `useChatSummary(chatId)` hook

- `useQuery(['chats', id, 'summary'])` → `GET`.
- `useMutation` → `POST`; on success writes the result into the query cache.
- Effect: when the GET result is `stale && !generating` and no mutation is
  pending or has errored for this state, fire the mutation once.
- While `generating` (or POST returned 409), `refetchInterval: 2000` on the
  GET until `generating` is false; then the effect above re-evaluates.
- Retry button calls `mutation.mutate()` and clears the error.

### 6.4 `ChatSummaryCard` states

| State                                 | UI                                                                        |
| ------------------------------------- | ------------------------------------------------------------------------- |
| GET loading                           | Skeleton lines (`animate-pulse`, respects reduced motion)                 |
| No summary, generating / POST pending | Skeleton + spinner + "Generating summary…" (`role="status"`, `aria-live`) |
| Summary, stale, updating              | Old text dimmed + spinner + "Updating with N new messages…"               |
| Ready                                 | Text + "Updated ‹date› · ‹model›"                              |
| Error                                 | Old text if any + alert with message + "Retry"                            |
| `content === null && !stale`          | "Nothing to summarize yet."                                               |

Styling follows existing admin Tailwind tokens (`text-fg-muted`, `border-border`,
`text-danger`, `text-accent`).
